# Step 4 — Server Functions for Registration

> Part of the [Registration Leptos Migration Plan](registration-leptos-migration.md).

**Goal:** Create Leptos server functions that wrap the three GraphQL mutations (`verifyReferralString`, `register`, `verifyAccount`). These functions run on the Axum server and are automatically callable from client-side WASM via generated HTTP endpoints. They bridge the type-safe GraphQL client (Step 3) and the reactive UI components (Steps 6–9).

## 4.2 — Architecture Overview

Server functions are Leptos's built-in RPC mechanism. The `#[server]` macro generates:
1. A server-side async function that runs natively on Axum
2. A client-side stub that serializes arguments, sends `POST /api/<fn_name>`, and deserializes the response
3. Automatic `ServerFnError` wrapping for any errors

```
┌──────────────────────────────────────────────────────────────┐
│                  Client (WASM in browser)                     │
│                                                              │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  RegisterPage component                                │  │
│  │    create_action(verify_referral)                       │  │
│  │    create_action(register_user)                         │  │
│  └─────────────────────┬──────────────────────────────────┘  │
│                        │ POST /api/verify_referral           │
│                        │ POST /api/register_user             │
│                        │ POST /api/verify_account            │
└────────────────────────┼─────────────────────────────────────┘
                         │ HTTP (auto-generated by #[server])
┌────────────────────────┼─────────────────────────────────────┐
│                  Server (Axum, native Rust)                   │
│                        ▼                                     │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  src/api/registration.rs                               │  │
│  │    verify_referral()  → graphql::mutate()              │  │
│  │    register_user()    → graphql::mutate()              │  │
│  │    verify_account()   → graphql::mutate()              │  │
│  └─────────────────────┬──────────────────────────────────┘  │
│                        │                                     │
│  ┌─────────────────────▼──────────────────────────────────┐  │
│  │  src/api/graphql.rs (Step 3)                           │  │
│  │    mutate<V, R>() → reqwest POST to GraphQL endpoint   │  │
│  └────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────┘
                         │
                         ▼
┌──────────────────────────────────────────────────────────────┐
│            Mock Backend / Production GraphQL API              │
│                  http://localhost:4000/graphql                │
└──────────────────────────────────────────────────────────────┘
```

### Key Design Decisions

| Decision | Rationale |
|----------|-----------|
| One server function per mutation | Keep a 1:1 mapping for clarity; each can be independently `create_action`'d in UI components |
| Accept primitive / simple struct args | Server function arguments must impl `Serialize + DeserializeOwned`; `RegistrationInput` already does |
| Return domain types, not raw GraphQL wrappers | Unwrap the `{ data: { mutationName: { ... } } }` envelope inside the server function so UI components receive clean types |
| Transform `ApiError` → `ServerFnError` | Leptos requires `ServerFnError`; provide a `From` impl for ergonomic `?` usage |
| Server-side input validation | Validate referral UUID format and required fields on the server before hitting GraphQL — defense in depth |
| No auth tokens (yet) | Registration mutations are unauthenticated; token handling will be added when login is implemented |

## 4.3 — Error Conversion: `ApiError` → `ServerFnError`

Before writing the server functions, we need a `From` impl so the `?` operator works seamlessly.

### Update `src/models/common.rs`

Add the following `impl` block after the existing `ApiError` definition:

```rust
use leptos::prelude::ServerFnError;

impl From<ApiError> for ServerFnError {
    fn from(err: ApiError) -> Self {
        ServerFnError::new(err.to_string())
    }
}
```

This allows server functions to do:

```rust
let data = mutate(...).await?;  // ApiError auto-converts to ServerFnError
```

## 4.4 — Server-Side Input Validation

Create a small validation module to sanity-check inputs before they reach the GraphQL layer. This is defense-in-depth — the client will also validate, but server functions are publicly accessible HTTP endpoints.

### Create `src/api/validation.rs`

```rust
//! Server-side input validation for registration server functions.
//!
//! These checks run on the Axum server before any GraphQL call is made.
//! They provide fast rejection of obviously invalid input and protect
//! against malformed requests that bypass client-side validation.

use crate::models::common::ApiError;

/// Validate that a string looks like a UUID v4.
///
/// Accepts the format: `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`
/// where `x` is a hex digit. Does not enforce v4 variant bits.
///
/// # Examples
///
/// ```
/// assert!(validate_uuid("85d5f836-b1f5-4c4e-9381-1b058e13df93").is_ok());
/// assert!(validate_uuid("not-a-uuid").is_err());
/// assert!(validate_uuid("").is_err());
/// ```
pub fn validate_uuid(s: &str) -> Result<(), ApiError> {
    let uuid_pattern = regex::Regex::new(
        r"^[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}$"
    ).expect("UUID regex is valid");

    if uuid_pattern.is_match(s) {
        Ok(())
    } else {
        Err(ApiError::Api {
            code: "31010".to_string(),
            message: "Invalid referral code format".to_string(),
        })
    }
}

/// Validate registration input fields on the server side.
///
/// Checks:
/// - Email is non-empty and has a basic valid format
/// - Username is 3–23 characters, alphanumeric with `_` and `-`
/// - Password is at least 8 characters
///
/// These mirror the client-side checks but are intentionally more lenient —
/// the real validation authority is the backend GraphQL API.
pub fn validate_registration_input(
    email: &str,
    username: &str,
    password: &str,
) -> Result<(), ApiError> {
    // Email: basic format check
    if email.is_empty() || !email.contains('@') || !email.contains('.') {
        return Err(ApiError::Api {
            code: "30103".to_string(),
            message: "Invalid email format".to_string(),
        });
    }

    // Email: length sanity check (RFC 5321 limit is 254)
    if email.len() > 254 {
        return Err(ApiError::Api {
            code: "30103".to_string(),
            message: "Email address too long".to_string(),
        });
    }

    // Username: 3-23 chars, alphanumeric + underscore + hyphen
    let username_pattern = regex::Regex::new(r"^[a-zA-Z0-9_-]{3,23}$")
        .expect("Username regex is valid");

    if !username_pattern.is_match(username) {
        return Err(ApiError::Api {
            code: "30202".to_string(),
            message: "Invalid username format".to_string(),
        });
    }

    // Password: minimum 8 characters
    if password.len() < 8 {
        return Err(ApiError::Api {
            code: "30103".to_string(),
            message: "Password must be at least 8 characters".to_string(),
        });
    }

    Ok(())
}

## 4.5 — Server Functions File: `src/api/registration.rs`

This is the core deliverable of Step 4. Create `src/api/registration.rs`:

```rust
//! Leptos server functions for the registration flow.
//!
//! These functions are the bridge between client-side WASM components
//! and the backend GraphQL API. Each function:
//!
//! 1. Runs on the Axum server (never in WASM)
//! 2. Validates input (defense-in-depth)
//! 3. Calls the GraphQL API via `api::graphql::mutate`
//! 4. Unwraps the GraphQL data envelope
//! 5. Returns clean domain types to the caller
//!
//! From the client side, these are called like normal async functions:
//! ```rust,ignore
//! let result = verify_referral("85d5f836-...".into()).await;
//! ```
//!
//! Leptos auto-generates the corresponding `POST /api/<fn_name>` endpoint.

use leptos::prelude::*;

use crate::models::user::{
    ReferralVerifyResponse, RegisterResponse, RegistrationInput, VerifyAccountResponse,
};

// ============================================================================
// Server function: Verify Referral Code
// ============================================================================

/// Verify a referral code against the backend.
///
/// Validates the UUID format on the server side, then calls the
/// `verifyReferralString` GraphQL mutation.
///
/// # Arguments
///
/// - `referral_string`: A UUID string (e.g., `"85d5f836-b1f5-4c4e-9381-1b058e13df93"`)
///
/// # Returns
///
/// - `Ok(ReferralVerifyResponse)` — contains `status`, `response_code`, and
///   optionally `affected_rows` with the referring user's info
/// - `Err(ServerFnError)` — on validation failure, network error, or GraphQL error
///
/// # Generated endpoint
///
/// `POST /api/verify_referral` with JSON body `{ "referral_string": "..." }`
#[server(VerifyReferral, "/api")]
pub async fn verify_referral(
    referral_string: String,
) -> Result<ReferralVerifyResponse, ServerFnError> {
    use crate::api::graphql::{mutate, VerifyReferralData, VERIFY_REFERRAL_MUTATION};
    use crate::api::validation::validate_uuid;

    // 1. Server-side validation
    validate_uuid(&referral_string)?;

    // 2. Build variables matching the GraphQL mutation signature
    #[derive(serde::Serialize)]
    #[serde(rename_all = "camelCase")]
    struct Vars {
        referral_string: String,
    }

    let variables = Vars { referral_string };

    // 3. Call the GraphQL API
    let data: VerifyReferralData =
        mutate(VERIFY_REFERRAL_MUTATION, variables, None).await?;

    // 4. Unwrap the GraphQL envelope and return the domain type
    Ok(data.verify_referral_string)
}

// ============================================================================
// Server function: Register User
// ============================================================================

/// Register a new user account.
///
/// Validates input fields on the server side, then calls the `register`
/// GraphQL mutation. On success, the response includes the new user's ID
/// which is needed for the subsequent `verify_account` call.
///
/// # Arguments
///
/// - `email`: User's email address
/// - `password`: User's chosen password (min 8 chars)
/// - `username`: Desired username (3–23 chars, alphanumeric + `_-`)
/// - `referral_uuid`: UUID of the referring user (from Step 1 of the flow)
///
/// # Returns
///
/// - `Ok(RegisterResponse)` — contains `status`, `response_code`, and `userid`
/// - `Err(ServerFnError)` — on validation, network, or GraphQL error
///
/// # Generated endpoint
///
/// `POST /api/register_user` with JSON body containing all fields
///
/// # Response codes
///
/// - `10601` — Registration successful
/// - `30601` — Email already registered
/// - `40601` — Server error
/// - `40602` — Failed to generate user ID
#[server(RegisterUser, "/api")]
pub async fn register_user(
    email: String,
    password: String,
    username: String,
    referral_uuid: String,
) -> Result<RegisterResponse, ServerFnError> {
    use crate::api::graphql::{mutate, RegisterData, REGISTER_MUTATION};
    use crate::api::validation::{validate_registration_input, validate_uuid};

    // 1. Server-side validation
    validate_registration_input(&email, &username, &password)?;
    validate_uuid(&referral_uuid)?;

    // 2. Construct the RegistrationInput
    let input = RegistrationInput::new(&email, &password, &username)
        .with_referral(referral_uuid);

    // 3. Build variables matching the GraphQL mutation signature
    #[derive(serde::Serialize)]
    struct Vars {
        input: RegistrationInput,
    }

    let variables = Vars { input };

    // 4. Call the GraphQL API
    let data: RegisterData = mutate(REGISTER_MUTATION, variables, None).await?;

    // 5. Return the domain type
    Ok(data.register)
}

// ============================================================================
// Server function: Verify Account
// ============================================================================

/// Verify a newly registered account.
///
/// Called immediately after a successful registration to activate the account.
/// In the current Peer flow, this is triggered automatically (not by the user
/// clicking an email link).
///
/// # Arguments
///
/// - `userid`: The user ID returned by the `register` mutation
///
/// # Returns
///
/// - `Ok(VerifyAccountResponse)` — contains `status` and `response_code`
/// - `Err(ServerFnError)` — on network or GraphQL error
///
/// # Generated endpoint
///
/// `POST /api/verify_account` with JSON body `{ "userid": "..." }`
///
/// # Response codes
///
/// - `10701` — Account verified successfully
/// - `30701` — Account already verified
/// - `40701` — Verification server error
#[server(VerifyAccount, "/api")]
pub async fn verify_account(userid: String) -> Result<VerifyAccountResponse, ServerFnError> {
    use crate::api::graphql::{mutate, VerifyAccountData, VERIFY_ACCOUNT_MUTATION};

    // 1. Basic validation — userid should be non-empty
    if userid.trim().is_empty() {
        return Err(ServerFnError::new("User ID is required"));
    }

    // 2. Build variables matching the GraphQL mutation signature
    #[derive(serde::Serialize)]
    #[serde(rename_all = "camelCase")]
    struct Vars {
        user_id: String,
    }

    let variables = Vars { user_id: userid };

    // 3. Call the GraphQL API
    let data: VerifyAccountData =
        mutate(VERIFY_ACCOUNT_MUTATION, variables, None).await?;

    // 4. Return the domain type
    Ok(data.verify_account)
}
```

```rust

let app = Router::new()
    .leptos_routes(&leptos_options, routes, {
        let leptos_options = leptos_options.clone();
        move || shell(leptos_options.clone())
    })
    // ... existing middleware ...
    ;

> **Note:** With `cargo-leptos` and the `#[server]` macro, server functions are typically auto-registered when using the standard Leptos Axum integration. //! Integration tests for registration server functions.
//!
//! These tests call the server functions via their HTTP endpoints,
//! simulating what the WASM client does. They require:
//! 1. The mock backend running on port 4000
//! 2. The Leptos dev server running on port 3000
//!

#![cfg(feature = "ssr")]

use reqwest::Client;
use serde::Deserialize;
use serde_json::json;

const SERVER_URL: &str = "http://localhost:3000";

/// Helper: POST to a server function endpoint and parse the response.
async fn call_server_fn<T: for<'de> Deserialize<'de>>(
    path: &str,
    body: serde_json::Value,
) -> Result<T, String> {
    let client = Client::new();
    let response = client
        .post(format!("{}{}", SERVER_URL, path))
        .header("Content-Type", "application/json")
        .header("Accept", "application/json")
        .json(&body)
        .send()
        .await
        .map_err(|e| format!("Request failed: {}", e))?;

    let status = response.status();
    let text = response
        .text()
        .await
        .map_err(|e| format!("Failed to read body: {}", e))?;

    if !status.is_success() {
        return Err(format!("HTTP {}: {}", status, text));
    }

    serde_json::from_str(&text).map_err(|e| format!("Deserialize error: {} (body: {})", e, text))
}

## 4.12 — Common Issues & Solutions

| Issue | Cause | Solution |
|-------|-------|----------|
| `#[server] macro not found` | Missing `leptos` feature or import | Ensure `use leptos::prelude::*;` and `features = ["ssr"]` in Cargo.toml |
| `ServerFnError` not implementing `From<ApiError>` | Missing conversion | Add the `impl From<ApiError> for ServerFnError` in `models/common.rs` (§4.3) |
| `POST /api/verify_referral` returns 404 | Server functions not registered | Check Axum router configuration (§4.6.2); run `cargo leptos watch` not `cargo run` |
| `reqwest` not found in WASM build | `reqwest` used outside `#[cfg(feature = "ssr")]` | Ensure `reqwest` calls are only in server-gated code; `#[server]` does this automatically |
| Variable serialization mismatch | Field names don't match GraphQL variables | Check `#[serde(rename_all = "camelCase")]` on variable structs |
| `regex` crate bloats WASM bundle | `regex` compiled into client | Gate `validation.rs` with `#[cfg(feature = "ssr")]` (already done in §4.6.1) |
| Integration tests fail with connection refused | Leptos server not running | Start with `cargo leptos watch` in a separate terminal |
| Duplicate email test flaky | Mock backend state not reset between runs | Use unique emails with `uuid::Uuid::new_v4()` (already done in tests) |

### Regex-free alternative

If you want to avoid the `regex` dependency, replace `validate_uuid` with a manual parser:

```rust
pub fn validate_uuid(s: &str) -> Result<(), ApiError> {
    let bytes = s.as_bytes();
    if bytes.len() != 36 { return Err(/* ... */); }
    for (i, &b) in bytes.iter().enumerate() {
        match i {
            8 | 13 | 18 | 23 => {
                if b != b'-' { return Err(/* ... */); }
            }
            _ => {
                if !b.is_ascii_hexdigit() { return Err(/* ... */); }
            }
        }
    }
    Ok(())
}
```

This eliminates the `regex` crate entirely, reducing compile time.

## 4.13 — Security Considerations

| Concern | Mitigation |
|---------|------------|
| **Passwords logged in server output** | Server functions do not log input values; `password` is never printed in error messages |
| **Server functions accessible without CSRF protection** | Leptos server functions use same-origin POST with JSON content type, which browsers don't send cross-origin without CORS pre-flight. Add explicit CSRF tokens in a later step if needed |
| **Input injection** | Server-side validation rejects malformed input before it reaches GraphQL; the GraphQL API itself parameterizes all inputs |
| **Endpoint enumeration** | Server function paths (`/api/*`) are predictable by design; authentication will be added for protected endpoints in the login migration |
| **Rate limiting** | Not implemented in this step; add Axum middleware (e.g., `tower-governor`) in a future hardening step |
